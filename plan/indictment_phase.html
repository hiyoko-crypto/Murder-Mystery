Phase 2 of 2 — 起訴

起訴フェーズの実装

プレイヤーが容疑者を指名し、理由を述べ、勝敗が決まるまでの現在の実装。Phase 1（捜査）で集めた情報がここでどう評価されるかをまとめる。

判定対象エッジ: 20 / 全137エッジ中 最低スコア: 5 抽出リトライ: 最大3回

1起訴の全体フロー

suspect_agents/run_game_kg.pyのCLI上での流れ:

  1. 尋問メニューで「犯人を指名する」を選ぶ（会話済みかどうかに関わらず、いつでも選べる）。
  2. 容疑者を1人選ぶ。
  3. 理由を自由記述で入力する（日本語可）。
  4. session.indict(suspect_id, reason) → GameSession.indict() → evaluate_indictment()が呼ばれる。
  5. スコア・成立した証明グループ・不足している必須グループが表示される。
  6. 勝敗と、勝った場合はsolution.explanation（事件の解説文）が表示され、プロセスはsys.exit(0)で終了する。
設計上の判断

起訴は１ゲームにつき1回きりの最終アクションで、成功しても失敗してもゲームが終わる。捜査フェーズのように何度もやり直せる会話とは性質が異なるため、判定ロジックはLLMの気まぐれに委ねずルールベースの決定的な採点にしている（§3）。

  "explanation": "Elena entered Marcus's locked dressing room via the ventilation shaft..."
}

5つのグループが合わせて参照する実エッジ数は20（137エッジ中約15%）。各グループは「これだけの種類の証拠のうちN個以上に触れていればこのグループは通過」というAND/OR混在の採点単位で、weightを持ち、required: trueのグループが1つでも未達なら他がどれだけ高得点でも不合格になる。エッジIDはシナリオ整理のたびに振り直されるため、ここに載せた具体的なID自体を将来のリファレンスとして当てにしないこと——構造（グループ構成・weight・min_required）が本質。

フィールド意味
killer_node正解の容疑者ノードID。指名との一致は文字列比較のみ、LLMを介さない。
key_evidence_edges事件の核心となるエッジ一覧。採点コードからは参照されていない参考情報。
red_herring_edgesミスリードとなる証拠。こちらも採点コードからは参照されていない。

3判定ロジック（modules/indictment_evaluator.py）

_proof_graph_subgraph(groups, nodes, edges)

proof_graph.groups[].edge_idsの和集合（20エッジ）と、その両端のノードだけを取り出す。理由文抽出（§4）にはこの絞り込んだサブグラフだけが渡され、シナリオ全体（137エッジ・77ノード）は渡さない。

evaluate_indictment(accused_node_id, reason_text, loader)

accused_correct = accused_node_id == solution["killer_node"]          # 文字列比較のみ
extraction = extract_reason_edges(reason_text, scoped_nodes, scoped_edges, ...)
mentioned_edge_ids = set(extraction["mentioned_edge_ids"])

passed_groups, failed_groups, score = _evaluate_groups(mentioned_edge_ids, groups)
failed_required_groups = [g for g in failed_groups if g["required"]]

reason_accepted = not failed_required_groups and score >= minimum_score
won = accused_correct and reason_accepted

_evaluate_groups()は各グループについてedge_ids ∩ mentioned_edge_idsを取り、min_required以上あれば通過、通過分のweightを合計して総スコアにする。wonは「正しい容疑者」かつ「必須グループを全通過」かつ「最低スコア以上」の3条件がすべて揃って初めて真になる。

GameSession.indict() でのメッセージ選択

accused_correctreason_accepted結果
✓✓勝利。solution.explanationを表示。
✗—不正解。「{容疑者}は犯人ではない」。
✓✗容疑者は正しいが証拠不十分。「reasoning does not establish the case」。

4理由文からのエッジ抽出（modules/reason_edge_extractor.py）

自由記述の理由文を、どのKGエッジに言及しているかにマッピングするのがこのモジュールの唯一の役割。事件を解いたり、勝敗を判断したりはしない——それは§3の完全にルールベースな側の仕事。

プロンプトが要求する出力

{
  "claims": [{"text": "...", "quote": "..."}],
  "mentioned_edges": [
    {"edge_id": "e7", "confidence": 0.92, "matched_claim": "...", "quote": "..."}
  ]
}

confidenceがCONFIDENCE_THRESHOLD = 0.6以上のエッジだけがmentioned_edge_idsとして採用される。日本語・英語どちらの理由文にも対応し、表記ゆれや意訳、固有名詞の日本語表記（display_names_ja）も許容するよう指示している。

JSON検証つきリトライループ

suspect_agents/validator_kg.pyと同じパターンで、MAX_RETRIES = 3回まで再試行する。 

for attempt in range(MAX_RETRIES):
    raw = llm(prompt, temperature=0.0)
    parsed, error = _parse_response(raw)   # json.loads に失敗 or dict でなければ error
    if error is None:
        return {...}                       # 成功
    prompt = base_prompt + f"\n\n[Previous output was invalid: {error}. Return valid JSON only...]"
# 3回とも失敗したら空の mentioned_edge_ids + llm_error を返す（安全側フォールバック）

5設計上の判断

なぜグラフ全体ではなく20エッジだけを渡すのか

以前は全150エッジ・77ノードの説明文（約6,900トークン）をまるごとLLMに渡していたが、これは会話用に設定されたNUM_CTX = 4096を大きく超えていた。proof_graphが実際に採点で使うのは20エッジだけであり、残りはLLMが「捏造かどうか」を判断するための参考材料に過ぎなかった（次項）。20エッジ＋その両端ノードに絞ることでプロンプトは約1,800トークンまで縮小し、コンテキスト予算内に収まるようになった。

なぜ「捏造判定」と「矛盾判定」を廃止したのか

以前は抽出結果にinvented_major_claims（KGに存在しない主張の検出）とcontradicted_edges（既知の事実との矛盾）も含めていた。しかしcontradicted_edgesはreason_acceptedの判定に一度も使われておらず、計算されるだけの死んだ値だった。invented_major_claimsは判定に使われていたが、正確に機能させるにはグラフ全体の可視性が必要で、それこそが上記のコンテキスト超過の直接の原因だった。核心的な勝敗判定（score >= minimum_scoreかつ必須グループ充足）はすでに「十分な量の実在する証拠を正しく言えたか」だけで成立しており、捏造判定がなくても機能する。費用（グラフ全体を渡す必要）と便益（限定的な不正防止）を比較し、廃止した。

確認済みの効果

解決編の説明とほぼ同じ内容（コンパクトの所有・換気シャフトの接続）を理由文にした場合、変更前はスコア0/5で不合格になっていたが、変更後はスコア6〜7/5で正しく勝利判定される。根拠のない理由文（「なんとなく怪しいから」）や、誤った容疑者を指名した場合は、変更後も正しく不合格になることを確認済み。

なぜリトライループを追加したのか

プロンプトを縮小した後も、ローカルLLM（qwen3.5:9b）がまれに指示されたJSON形式を無視することがある（数回に1回程度）。コンテキスト超過が原因ではなく、モデル自体の残存する不安定さ。会話生成側のvalidator_kg.pyにすでにある「検証失敗時にエラーをヒントとして再送する」パターンをそのまま踏襲し、1回の起訴判定の信頼性を高めている。

6既知の制約

  • key_evidence_edges / red_herring_edgesは未使用 — solutionに定義されているが、indictment_evaluator.pyのどこからも参照されていない。将来「ミスリードだけで押し切った起訴」を弾くような仕組みを作るなら、ここが起点になり得る。
  • 矛盾検出は現在存在しない — 「間違った前提（例: 凶器を取り違える）で偶然正しい容疑者を当てる」ことを防ぐ仕組みは、捏造判定と一緒に廃止して以降ない。必要なら20エッジの範囲内で再導入する余地はある。
  • 抽出はLLM依存のまま — リトライで信頼性は上がったが、3回とも失敗する確率はゼロではない。3回とも失敗した場合、正しい理由文でも証拠0件として不合格になる。

Phase 1 of 2 — 捜査

捜査フェーズの実装

プレイヤーが容疑者に尋問し、現場を調査し、場所やアイテムを発見していく――起訴（Phase 2）に至るまでの全プロセスの現在の実装をまとめる。

対象シナリオ: the_final_act.json ノード: 77 エッジ: 150（rel種別 96） 容疑者: 3（Elena / Julian / Leo）

  • suspect_agents/run_game_kg.py — ファイル冒頭に「ゲームロジックは全てgame_session.pyにあり、ここは入出力だけを扱う」と明記されている通りの純粋なCLI I/O層。session.get_briefing() / get_examine_options() / examine_location() / examine_item() / switch_suspect() / ask() / get_state() / indict()——GameSessionの公開APIだけを呼ぶ。

容疑者切替専用のエンドポイントは存在せず、/chat1本がswitch_suspectとaskを毎回まとめて実行する。フロントエンドは「今どの容疑者と話しているか」を意識せず、常に「この容疑者にこのメッセージを送る」という単位でリクエストできる。

2シナリオデータモデル

scenarios/the_final_act.jsonのトップレベルキーは scenario_id / title / setting / murder_details / knowledge_graph / suspects / examine_rules / solution / display_names_ja。 solution（proof_graph含む）は起訴判定専用なのでPhase 2のドキュメントで扱う。

knowledge_graph.nodes（77件）

各ノードは {"id", "labels": [...], "properties": {...}}。labelsはフラットなtypeではなく配列で、粒度の異なるラベルを重ねられる。例えば被害者は["Character","Victim"]、凶器は["Item","MurderWeapon"]。イベント系ノードはさらに細分化されており、["Event","VisitEvent"] ["Event","MovementEvent"] ["Event","CrimeEvent"] ["Event","PresenceEvent"] ["Event","TamperingEvent"]など、ファイル全体で35通りのラベルの組み合わせが存在する。

プロパティはノードの種類によって異なる。人物ならname / role / bio / tags / interrogation_style（容疑者のみguilty: bool）、アイテムならname / description / significance、時間軸を持つノードはtimeまたはstart_time/end_timeを持つ。

knowledge_graph.edges（150件）

{"id": "e14", "from": "n_elena", "to": "n_marcus", "rel": "STRUCK",
 "properties": {"known_by": ["n_elena"], "provenance": "self_knowledge",
                "hidden_from_detective": true, "time": "9:05 PM"}}
  • known_by（150/150に存在）— "all"（全員が知る公開事実、43件）／容疑者ノードIDの配列（自己知識）／[]（誰も語れず、examineでしか判明しない事実、40件）。
  • hidden_from_detective: true（18件）— 容疑者は知っているが、探偵には決して口にしてはならない事実。
  • provenance（150/150）— self_knowledge / direct_observation / public_report / public_hearsay / discoverable_evidence。プロンプト内でエッジをグルーピングする際に使われる（§3）。
  • player_discovery（44/150）— {"method": "examine_location", "target": "..."}のような形。詳細は§7参照。

examine_rules

{"locations": {...}, "items": {...}}。場所ごとにinitially_available / unlock_from_testimony / unlock_from_item（任意）/ items_present / description。アイテムごとにunlocks_location（あれば場所IDを指す）。§4のアンロック機構が参照する。

ScenarioLoader（modules/scenario_loader.py）

JSONを一度だけ読み込み、self.nodes / self.edgesをID索引化する。中心的なメソッドはget_subgraph(node_id) ――「この容疑者は何を知っているか」を返すクエリで、全エッジを走査し、known_byとhidden_from_detectiveでvisible_edges / hidden_edgesに振り分ける。

設計上の判断

「誰が何を知っているか」を容疑者ごとのハードコードされたリストではなくエッジ側のプロパティとして持たせている。これにより、ある事実を誰に知らせるかの変更はJSON側の1行の編集で完結し、プロンプト生成・隠蔽漏洩チェック・場所開放のすべてに自動的に反映される。容疑者固有のコード変更は不要。

3容疑者との会話パイプライン

プロンプト構築（modules/subgraph_to_prompt.py）

build_system_prompt(subgraph, nodes, ledger_text)が、可視エッジをprovenanceで personal（自己知識・直接観察＝「自分の経験として語ってよい」）／public（公開報告・伝聞＝「自分の体験のように語ってはいけない」）／other にグルーピングし、隠蔽エッジは[Facts you know but must NOT reveal]ブロックとして別枠で渡す。末尾で自己申告グラフ（後述）と、厳格なJSON出力形式の指示を付ける。 

{"response": "...", "used_edge_ids": ["e14", "e19"], "asserted_triples": [["Elena","WAS_IN","ElenaRoom @ 9:10 PM"]]}

asserted_triplesの指示は「本文で明言した事実だけ」「時刻があればオブジェクト側に@ timeで付与」「以前の自己申告と同じ事実を今回も述べた場合以外は繰り返さない」の3点を明示している。当初は単に「応答から抽出できる事実」とだけ指示していたが、実際には本文で言っていない背景知識まで大量に自己申告したり、内容が変わっても前ターンと同じトリプルをそのまま繰り返したりする挙動が見られたため、この3点を明文化した。

応答生成と検証のリトライループ（suspect_agents/suspect_agent_kg.py）

  1. 日本語モードなら、質問をまず英語に翻訳する（translate_question_to_english）。KG上の推論はUI言語に関わらず常に英語で行われる。
  2. CommitmentLedger.get_self_graph_text()で自己申告グラフを組み立て、システムプロンプトに載せてllm_messages()を呼ぶ（temperature=0.7）。
  3. validator_kg.validate_response()で検証。失敗したら[Previous output was invalid: {error}...]というヒントを追記して再送——最大MAX_RETRIES = 3回。
  4. 成功したらused_edge_idsをlast_used_edge_idsとして保持（§4の場所開放が参照）、台帳に記録、日本語モードなら応答を翻訳して返す。
  5. 3回とも失敗した場合は安全な定型応答（"I need a moment to collect myself..."）にフォールバックする。

validate_response() が実際にチェックしていること（suspect_agents/validator_kg.py）

  • JSON抽出＋パースが成功するか
  • response / used_edge_ids / asserted_triplesの型が正しいか
  • 漏洩チェック: used_edge_ids ∩ hidden_edge_idsが空か
  • グラウンディングチェック: used_edge_idsが渡されたvisible_edge_idsの外を指していないか

CommitmentLedger と自己申告グラフ（suspect_agents/commitment_ledger.py）

容疑者IDごとにターン記録（質問・使用エッジ・主張トリプル・要約）を蓄積する。台帳はGameSessionに1つだけ存在し、全容疑者エージェントで共有される（容疑者ごとに別インスタンスではない）。

get_self_graph_text(node_id, max_turns=6)が、直近ターンのasserted_triplesをターンごとにグルーピングし、本物のKGエッジと同じ見た目（Subject --[REL]--> Object）で書き出す。これがプロンプトの[Your own prior statements this interrogation — maintain consistency]ブロックとしてそのまま渡される。 

Turn 1:
  Elena Rostova --[WAS_IN]--> Elena's Dressing Room @ 9:10 PM
Turn 2:
  Elena Rostova --[WAS_IN]--> Elena's Dressing Room @ 9:10 PM
設計上の判断

以前は「Turn N（edges: e1,e2）: 応答冒頭100文字」という自由文のプローズ要約をget_ledger_text()が生成しており、asserted_triples自体は矛盾チェック専用の内部データで容疑者本人には一切見せていなかった。本物のサブグラフと同じ書式に揃えた構造化テキストに置き換えることで、荒い100文字要約より正確に「自分が何を言ったか」を思い出せるようにしている。本物のサブグラフ（visible_edges）とは完全に別の変数として扱っており、グラウンディングチェックの対象には含まれない。

留意点

以前はcheck_contradiction()という「同じ(主語,関係)の組に対して、以前と異なる目的語を主張した場合を矛盾とみなす」文字列完全一致ベースの矛盾チェックがvalidate_response()から呼ばれていたが、削除した。asserted_triplesはLLMの自己申告した自由文字列で、同じ事実でも言い回しが変わるだけ（時刻の有無を含む）で「別の目的語」と誤判定され、実際には矛盾していない言い直しを不要にリトライさせるリスクの方が大きいと判断したため。意味レベルでの矛盾検出は、無効化されている「セマンティックバリデータ」（ENABLE_SEMANTIC_VALIDATOR、次項）側の役割として残されている。

設計上の判断

意味レベルの矛盾やほのめかしを拾う「セマンティックバリデータ」は実装済みだが、現在はENABLE_SEMANTIC_VALIDATOR = Falseで無効化されている。1ターンあたりのLLM呼び出し回数がほぼ3倍（質問翻訳＋本応答＋意味検証＋各リトライ）に増えるためと見られる。

4場所・アイテムの開放（modules/location_tracker.py）

機構1: アイテム連鎖によるアンロック

examine_item(item_id)がexamine_rules.items[item_id].unlocks_locationを見て、あれば新しい場所として開放する。例: 「換気口の格子」を調べると「換気ダクト」が開放される。

機構2: 証言によるアンロック

容疑者が回答するたびに、unlock_from_testimony(used_edge_ids, speaker_id)が呼ばれる。使用されたエッジがspeaker --[WAS_IN]--> locationなら直接、あるいはspeaker --[PARTICIPATED_IN]--> eventのようなイベント参加エッジなら、そのイベントから--[OCCURRED_AT]-->で辿れる場所を候補にする。候補の場所にunlock_from_testimony: trueが設定されていれば開放される。

設計上の判断

2つの機構があるのは、ミステリーにおける「発見」が本質的に2種類あるため。物理的探索（グレートを外すと通路が見える、という決め打ちの連鎖）と、言葉による発見（証言から「その場所」が浮かび上がる、というLLMの出力に依存する動的な連鎖）。後者はイベント経由の探索が必要なぶん、複雑なロジック（_testimony_location_refs）になっている。

5翻訳・多言語対応

modules/translator.pyはLLMベースのコンテンツ翻訳を担う3関数（質問のJA→EN、応答のEN→JA、UI/ゲーム内テキストのEN→JA）で、いずれもdisplay_names_ja（固有名詞のEN⇄JA対応表）をヒントとして渡す。GameSession._display_text()は結果をself._translation_cacheにメモ化し、同じ英文を二度翻訳しない。

modules/i18n.pyはCLI自身のUI文字列（メニュー・プロンプト等、約40キー）を保持する静的な辞書で、ゲーム内容の翻訳とは完全に別レイヤー。

設計上の判断

サブグラフ構築・検証・台帳・場所開放はすべて英語で動く。日本語は「入ってくる質問」と「出ていく応答・UI文言」という2つの境界だけに現れるプレゼンテーション層の関心事にすぎない。これによりKG/バリデータ側のロジックは言語非依存のまま保て、display_names_jaが両方向の翻訳で固有名詞の一貫性を保証する唯一の情報源になる。

6フロントエンド（概略）

  • contexts/ScenarioContext.tsx — /scenarioを一度取得し、displayNamesJaをクライアント側で適用した容疑者/場所/アイテムのアクセサを提供。
  • contexts/GameContext.tsx（実質的なuseGameState）— /stateをポーリングし、容疑者ごとの会話履歴はサーバーではなくReactのローカル状態で保持する。
  • api/scenario.tsのparseKgFormat() — knowledge_graphの生データから容疑者/場所/アイテムをクライアント側で独自に再導出している（バックエンドのScenarioLoader/LocationTrackerとは別実装）。
留意点

parseKgFormat()はノードのlabelsやエッジのrel名の命名規則にフロントエンド側で独自に依存している（例: アイテムの絵文字をキーワードマッチで推測）。バックエンドとフロントエンドの間にスキーマ/型の共有はなく、KGの命名を変えると両方を手動で追従させる必要がある。

7既知の食い違い・未整理点

コードを実際に読んで見つかった、仕様と実装がずれている・使われていない箇所。今回は修正せず記録のみ。

  • player_discoveryが未使用 — エッジの44件に付与されているが、Python側にもフロントエンド側にもこれを読むコードが存在しない。「どうやって発見されるべきか」の意図を表すメタデータのように見えるが、実際のアンロックはexamine_rulesだけで完結しており無関係。
  • ScenarioLoaderのレガシースキーマ対応は死んでいる — _has_known_byが常にTrueになる現在のシナリオでは、suspects[].subgraphベースの旧経路は到達しない。
  • ask_stream()はスタブ — game_session.pyに存在するが、内部でask()を1チャンクの疑似ジェネレータでラップしているだけ。llm_client.py自体がストリーミング未対応で、どのエンドポイントからも呼ばれていない。
  • examine系エンドポイントの動詞が不統一 — POST /examine/location/{id}に対しGET /examine/item/{id}。
  • api.pyがGameSessionの非公開属性を直接読む — /chatがgs._new_location_idsを直接参照している。小さなレイヤー違反。
  • llm_messages(quality=True)は無効 — 引数として受け取るがmodules/llm_client.py内で一度も使われていない。
  • セマンティックバリデータは実装済みだが無効 — ENABLE_SEMANTIC_VALIDATOR = False。有効化すれば意味レベルの漏洩・矛盾・捏造も検知できるが、現状は構文チェックのみで運用されている。

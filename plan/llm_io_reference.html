LLM入出力リファレンス

本プロジェクトでLLMを呼び出す箇所は大きく2つ——①容疑者の尋問応答、②起訴時の推理検証（自由文からKGエッジへのマッピング）。 どちらも「入力に何を渡すか」「出力に何を期待するか」が全く異なる設計になっている。実際のコード実行結果に基づく実例付きでまとめる。

1容疑者LLM（尋問応答）

suspect_agents/suspect_agent_kg_verbatim.py（本番実装）が毎ターン1回呼び出す。役割は「探偵の質問に、その容疑者が知っている事実の範囲内で自然に答える」こと。

1-1. 入力: messages配列

Ollamaのchat補完APIに渡すmessagesは3種類のメッセージから構成される。systemは毎ターン同じ内容で固定、過去のuser/assistantペアはターンを重ねるごとに増え続ける逐語履歴、最後に今回のuser質問が続く。

[system] 固定のシステムプロンプト
→
[user][assistant] × 過去のターン数
→
[user] 今回の質問
system message の内部構造
  1. キャラクター設定 — 名前・bio・personality tags・interrogation_style（キャラクターごとのJSONデータをそのまま埋め込み）
  2. [Facts you know] — この容疑者の可視エッジのみ。provenanceで personal（自己知識・直接観察）／public（伝聞・公開報告）／other の3グループに分けて列挙
  3. [Facts you know but must NOT reveal] — 隠蔽エッジ（hidden_from_detective: true）。存在する場合のみ追加
  4. [Output format] — 出力JSONのスキーマ指示

[Your own prior statements]ブロック（かつての構造化自己申告グラフ）は現在は使われていない — ledger_text=""で呼ぶため丸ごと省略され、代わりにmessages側の逐語履歴が同じ役割を果たす。

[Output format]

1-2. 過去の対話履歴（逐語履歴）の構造

容疑者の記憶は、かつてのように事実をトリプルへ要約したものではなく、実際に生成された生の発話をそのままchat_historyというリストに積み上げ、毎ターン丸ごと再送する方式（suspect_agents/suspect_agent_kg_verbatim.py）。 

self.chat_history: list = []  # {"role": ..., "content": ...} のプレーンなリスト。JSONではなく発話文そのもの

def get_suspect_response(self, user_message: str) -> str:
    ...
    system_msg = {"role": "system", "content": self.system_content}
    user_msg   = {"role": "user", "content": f"Detective: {question_for_llm}"}

    for attempt in range(MAX_RETRIES):
        messages = [system_msg] + self.chat_history + [user_msg]
        raw = llm_messages(messages, temperature=0.7, quality=True)

        is_valid, parsed, error = validate_response(...)
        if is_valid:
            response_text = parsed["response"]
            # 検証OKになった発話だけを履歴に追加する — JSONの生文字列ではなく
            # "response" フィールドの中身（プレーンな発話文）だけを保存する
            self.chat_history.append({"role": "user", "content": f"Detective: {question_for_llm}"})
            self.chat_history.append({"role": "assistant", "content": response_text})
            return response_text
  • 保存されるのは検証を通過した発話のみ — バリデータで弾かれた（＝再送された）試行はchat_historyには一切残らない
  • 保存する内容はused_edge_idsを含むJSON全体ではなく、responseフィールドのプレーンな発話文だけ
  • system messageは対象外 — 固定のキャラクター設定が毎ターン再送されるだけで、履歴には積まれない

留意点（plan/open_issues.md参照）

この配列はターンを重ねるごとに単調に増加する（要約や圧縮は一切行われない）。実測では10ターンの尋問でprompt_tokensが約2800→4030まで増加し、NUM_CTX = 4096（modules/llm_client.py）に接近してJSON生成が破綻する例も確認済み。まだ対策（最大ターン数の上限や古いターンの圧縮）は実装していない。

以前の方式との違い

保持されているsuspect_agents/suspect_agent_kg.py（トリプル方式・将来再利用の可能性ありのため削除せず保持）は、このchat_historyの代わりにCommitmentLedger.get_self_graph_text()が生成する構造化トリプル要約（最大直近6ターン、圧縮済み）をledger_textとしてsystem message内の別ブロックに埋め込む——messages配列自体は毎ターン[system, user]の2件だけで、履歴は積まれない。

留意点

system messageは毎ターン丸ごと再送される（キャラごとに固定・不変）。ターンを重ねるほどコンテキストが増えるのは逐語履歴側であり、system message自体のサイズは一定。

1-3. 出力: JSON

出力スキーマ 
{"response": "発話内容（英語）", "used_edge_ids": ["e13", "e14", ...]}
  • response — 容疑者としての発話。この文字列がそのまま（日本語モードなら翻訳して）画面に表示される
  • used_edge_ids — 今回の発話の根拠として使ったエッジID。ゲーム状態を動かす唯一の手がかり — 場所開放判定（location_tracker.py）はこの配列だけを見る

実例出力（Julian・ロビーの質問に対する実際の応答）

{
  "response": "I was in the front row of the stalls for the first act, Detective. I sat there
    from 7:30 until the curtain called at 9:00. After that, I moved to the lobby where I was
    with Barton and Finch until the show ended...",
  "used_edge_ids": ["e108", "e109", "e110", "e111", "e112", "e113", "e114", "e118"]
}

以前はasserted_triplesという第3フィールド（自己申告した事実をトリプル形式で書き出す）も要求していたが、記憶方式を逐語履歴に切り替えた際に誰も読まなくなったため、直近の変更でプロンプト・検証の両方から削除済み（生成させていない）。

検証ステップ（validator_kg.py）

この出力はvalidate_response()でJSONパース・型チェックの後、漏洩チェック（used_edge_idsに隠蔽エッジが含まれていないか）とグラウンディングチェック（可視エッジの範囲外を指していないか）を通過して初めて採用される。失敗した場合はエラーヒントを付けて最大3回まで再送。

1-4. hidden_edgeが漏洩した場合の再送プロンプト（実例）

容疑者LLMがused_edge_idsに隠蔽エッジを含めて返してしまった場合を実際に再現した例。Elenaの隠蔽エッジe12（Elena Rostova --[STRUCK]--> Marcus Vance）を含む出力をvalidate_response()に通すと、次のエラーが返る。 

raw output: {"response": "Fine, I did strike him with the candlestick, but it was self-defense!",
             "used_edge_ids": ["e14", "e12"]}

validate_response() の戻り値:
  is_valid = False
  error    = "hidden_edges が漏洩しています: ['e12']"

このerror文字列がそのまま次のuserメッセージに埋め込まれ、system messageは変更せずに同じターン内で即時再送される（chat_historyには失敗した試行は残らない）。 

[user] "Detective: Did you strike Marcus with the candlestick?

[Previous output was invalid: hidden_edges が漏洩しています: ['e12']. Please output valid JSON again.]"
留意点

エラーメッセージ自体（"hidden_edges が漏洩しています"）は日本語で書かれている。システムプロンプトや会話履歴はすべて英語で統一されているのに対し、バリデータのエラーヒントだけ日本語が混入する——LLMの理解には支障が出ていないようだが、プロンプト全体の言語一貫性としては小さな不整合。

この再送はMAX_RETRIES = 3回まで行われ、3回とも失敗した場合は安全な定型応答（"I need a moment to collect myself. Ask me again, Detective."）にフォールバックする。他に発生し得るエラー文字列は次の通り（いずれも同じ再送テンプレートに埋め込まれる）。

検証ステップエラー文字列の例
JSONパース失敗JSONパースエラー: Expecting ',' delimiter: ...
必須フィールド欠落'response' フィールドが存在しないか無効です / 'used_edge_ids' フィールドが存在しません
型不正'used_edge_ids' は配列である必要があります
隠蔽漏洩（上記の例）hidden_edges が漏洩しています: ['e12']
グラウンディング違反使用できないedge IDが含まれています: ['e999']（可視エッジの範囲外を指した場合）

2推理検証LLM（起訴判定）

modules/reason_edge_extractor.pyが呼び出す。役割は容疑者LLMと全く異なる——「探偵（プレイヤー）が自由文で書いた推理を、KGのエッジIDに変換すること」だけ。勝敗の判定そのものはLLMに一切させない。

2-1. 入力

毎起訴1回、llm()（単発プロンプト、temperature=0.0）を呼ぶ。渡すのはシナリオ全体のエッジ・ノードではなく、solution.proof_graphが参照しているエッジ・ノードだけに絞った部分グラフ——起訴判定エージェント版の「サブグラフ抽出」に相当する仕組み（_proof_graph_subgraph()）。

[knowledge graph edges] proof_graph参照分のみ（今回の例で19本）
[knowledge graph nodes and aliases] 上記エッジの端点ノード＋日本語表示名（今回の例で18件）
[player explanation] プレイヤーが書いた起訴理由の生テキスト

実例（proof_graph部分グラフ＋プレイヤーの理由文）

You map a player's murder accusation explanation to knowledge-graph edge IDs.

Task:
- Read the player's explanation, which may be in Japanese or English.
- Rewrite it into atomic factual claims.
- Map each claim to the KG edges it meaningfully mentions or paraphrases.
- Do not judge whether the accusation wins.
- Do not solve the case.
- Return only valid JSON.

- FOUND_IN: an item, person, or clue was found in a location.

- WAS_IN / PARTICIPATED_IN / OCCURRED_AT: a person or event was at a relevant place and time.

容疑者LLMとの違い

容疑者LLMは「この容疑者だけが知っている事実」に絞るのに対し、こちらは「proof_graphが採点対象にしているエッジ」だけに絞る——絞り込みの軸は違うが、どちらも全知識グラフを渡さずスコープを絞るという同じ設計思想。これはコンテキストオーバーフロー対策として明示的に選んだ実装（_proof_graph_subgraph()）。

2-3. LLM出力の後処理（ここは完全にPython・ルールベース）

indictment_evaluator.pyが、上記のLLM抽出結果（mentioned_edge_ids）とsolution.proof_graph（グループ・重み・最小要求数・必須フラグ・最小合格点）を照合し、LLMを一切使わずにスコアと勝敗を計算する。

ステップ内容
1accused_correct = 起訴した容疑者IDがsolution.killer_nodeと一致するか
2各proof_graphグループについて、mentioned_edge_idsとの積集合がmin_required本以上あれば合格、その重みをスコアに加算
3required: trueのグループが1つでも不合格なら、スコアに関わらずreason_accepted = False
4reason_accepted = 必須グループ全合格 かつ スコア ≥ minimum_score
5won = accused_correct かつ reason_accepted

実例の最終結果

{
  "accused_correct": true,
  "reason_accepted": true,
  "won": true,
  "score": 7,
  "minimum_score": 5,
  "passed_groups": ["compact_link (weight 4, required)", "vent_route (weight 2)", "locked_room (weight 1)"],
  "failed_groups": ["julian_presence_clears (weight 1)", "leo_cleared (weight 1)"]
}

言及しなかったjulian_presence_clears・leo_cleared（重み1ずつ、いずれもrequired: false）は不合格のままだが、必須グループcompact_linkを満たし合計スコアが最低点5を超えているため勝利になる。

32つのLLM呼び出しの比較

容疑者LLM推理検証LLM
呼び出し頻度探偵の質問1回ごと（容疑者切替ごとに独立）起訴1回につき1回だけ
入力の絞り込み軸その容疑者が知っている事実（可視/隠蔽）proof_graphが参照するエッジのみ

temperature0.7（自然な会話のばらつきを許容）0.0（マッピングの再現性を優先）
設計上の一貫したテーマ

両方とも「LLMにやらせるのは自然言語⇄構造化データの変換だけ」「最終的な正誤判定・状態遷移はコードの側で決定的に行う」という同じ方針で作られている。これがスライドで語るべき本プロジェクトのバックエンド設計の核。

# 発表スライド構成案（知識グラフ×殺人ミステリー尋問ゲーム）

過去の発表スライド2件（`Athena: Knowledge Graph-Enhanced AI Support For Graduate Admissions Study` / `ゲーム×知識グラフ(仮)`）の構成パターンを参考にまとめた、本プロジェクトの発表内容案。両デッキとも「背景 → システム概要 → 技術的工夫 → 評価実験 → デモ → 展望」という骨格が共通しているため、それに乗せる形で整理している。

## 1. タイトル・目次

- タイトル、メンバー、日付（他2件と同形式）
- 目次（Background / KGの設計 / 会話パイプライン / 起訴判定 / 評価実験 / デモ / 展望）

## 2. 背景・課題

- LLM単独ゲームの課題（Game×KGスライドp.4と同じ論点）: 過去の発言との一貫性が保証されない、ストーリーが収束しづらい
- 特にこのプロジェクトでは「有罪の容疑者が自白してしまう／過去の証言と矛盾する」という具体的な課題として提示できる
- 知識グラフで状態管理する狙い（Athenaスライドp.5「なぜ知識グラフか」と同じ論点が使える：一貫性保証、終了条件を定義しやすい）

## 3. ゲーム概要

- ルール説明：容疑者に尋問→場所やアイテムを調査→証拠を集めて起訴、の2フェーズ構成
- 知識グラフ＝シナリオの真実（`the_final_act.json`）：ノード/エッジ/`known_by`/`hidden_from_detective`/`provenance`
- イベントノードによる表現（誰が・どこで・いつ、をPARTICIPATED_IN/OCCURRED_ATで分解）— Athenaのnodes/edges説明（p.8, p.31）に相当する自分たちの独自設計として書ける

## 4. システム全体アーキテクチャ

- `main_kg.py`/`run_game_kg.py` → `GameSession` → 容疑者エージェント／`LocationTracker`／`CommitmentLedger`という構成図（Game×KGスライドp.11「ゲームの全体図」と同じ形式の図が作れる）
- フロントエンド／バックエンド構成（FastAPI + React、2言語セッション同時起動という独自ポイント）

## 5. 容疑者との会話パイプライン（このプロジェクトの核）

- サブグラフ抽出→プロンプト構築→LLM生成→バリデータ→リトライ、というフロー図
- **知識グラフをどう認識させるか**という課題はGame×KGスライドp.30-38と全く同じ論点を持っている：全体ではなく可視/隠蔽エッジに絞ったサブグラフのみ渡す、というのが自分たちの解決策として書ける
- 記憶方式の変遷（プローズ要約→構造化トリプル自己申告グラフ→検証済みの逐語履歴）— これは他2件にはない独自の工夫点として強調できる

## 6. 起訴フェーズ・判定ロジック

- `proof_graph`（グループ・重み・必須フラグ・最小スコア）による決定的スコアリング
- 「なぜLLMの holistic 判断ではなくルールベースにしたか」＝Athenaのconclusion的な設計判断として書ける
- 今回の会話で実際に確認した「間違った容疑者／根拠不足は正しく負け判定になる」という検証結果もここに入れられる

## 7. 評価実験（Game×KGスライドp.58-66と最も強く対応する章）

- **RAG版 vs KG版の比較実験**：現行のRAGレガシー実装を模した条件と、現行KG条件で「自白してしまうか」を比較 → 0/10 vs 4/10という定量結果
- 追加実験：ガード指示を入れたRAG条件、逐語履歴 vs 構造化トリプルの記憶方式比較（矛盾再現実験）
- Game×KGスライドの「総合評価0-10のテーブル」と同じ形式で結果表を作れる

## 8. デバッグ・品質改善の記録

- 発見・修正した重大バグ（起訴評価のコンテキストオーバーフロー、CLIの初期起訴分岐バグ）
- 知識グラフ自体の冗長性除去（イベントノード導入で発生した二重表現の整理、150→137エッジ）
- ログ収集・リトライ機構など、Game×KGスライドp.23-28「バックエンドの工夫点」に相当する運用面の工夫

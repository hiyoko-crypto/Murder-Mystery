サブグラフ生成方式の変更

2026-07-06 時点の変更メモ。容疑者ごとのサブグラフを JSON に手書きで保存する方式から、 全体 Knowledge Graph のエッジメタデータをもとに実行時へ導出する方式へ寄せる。

対象: backend / scenario JSON 主目的: 二重管理の削減 主目的: 知識範囲と発見条件の分離

結論

サブグラフはファイルとして保存しない。scenarios/the_final_act.json には全体 KG と エッジごとの known_by / provenance / player_discovery を保存し、 ScenarioLoader.get_subgraph(node_id) が実行時に容疑者ごとの visible_edges と hidden_edges を生成する。

生成されたサブグラフは各 SuspectAgentKG インスタンスの self.subgraph にメモリ上で保持され、質問ごとに LLM プロンプトへ渡される。

変更前の問題

問題 内容 影響
サブグラフの手書き管理 suspects[].subgraph.visible_edges に容疑者ごとの edge id を列挙していた。 全体 KG を変更したとき、各容疑者の edge list を更新し忘れると不整合が起きる。
visible_to の意味混在 キャラが知っている事実と、プレイヤーが調査で発見できる証拠が同じフィールドで表現されていた。 容疑者が本来知らない物証や他人のアリバイを話してしまう原因になる。
場所解放の混線 証言で使われた edge の from/to に場所が含まれると、その場所が解放され得る。 Julian の会話から Leo の Theatre Bar が解放されるような不自然な進行が起きる。

変更後のデータ設計

エッジの properties に、別々の意味を持つフィールドを分けて持たせる。

フィールド 意味 例
known_by この事実を知っているキャラ。"all"、容疑者 id の配列、または空配列。 ["n_julian"], "all", []
provenance その知識の由来。LLM が「自分の体験」と「噂・公的情報」を混同しないために使う。 self_knowledge, direct_observation, public_report, discoverable_evidence
player_discovery プレイヤーが調査で発見できる物証・事実の条件。 {"method": "examine_location", "target": "n_dressing_room"}
hidden_from_detective 犯人などが知っているが、探偵には明かしてはいけない事実。 true 
{
  "id": "e26",
  "from": "n_leo",
  "rel": "HAS_ALIBI",
  "to": "n_bar",
  "properties": {
    "time": "8:00 PM - 10:00 PM",
    "detail": "At the ground-floor bar all evening...",
    "known_by": ["n_leo"],
    "provenance": "self_knowledge",
    "player_discovery": {
      "method": "examine_location",
      "target": "n_bar"
    }
  }
}

実行時の流れ

1. GameSession 作成 GameSession が ScenarioLoader を初期化する。
2. SuspectAgent 作成 容疑者ごとに SuspectAgentKG を作る。
3. subgraph 導出 loader.get_subgraph(node_id) が known_by を見て edge を分類する。
4. LLM へ渡す build_system_prompt() が subgraph をプロンプト化する。 
GameSession(...)
  -> ScenarioLoader(...)
  -> SuspectAgentKG(loader, node_id, ledger)
       -> self.subgraph = loader.get_subgraph(node_id)
       -> ask(...)
            -> build_system_prompt(self.subgraph, self.loader.nodes, ledger_text)

実装された主な変更

ファイル 変更内容
modules/scenario_loader.py known_by から容疑者ごとの visible_edges / hidden_edges を導出する。
scenarios/the_final_act.json visible_to と手書き suspects[].subgraph を廃止し、エッジに known_by / provenance / player_discovery を追加。
modules/subgraph_to_prompt.py LLM に渡す事実を self_knowledge / direct_observation と public_report / public_hearsay に分けて提示する。
modules/location_tracker.py 証言による場所解放を、話者本人の HAS_ALIBI / WAS_IN に限定する。
game_session.py 場所解放時に agent.node_id を渡し、話者ベースで判定する。

期待される効果

  • 全体 KG と容疑者別 subgraph の二重管理がなくなる。
  • 容疑者が他人のアリバイや未発見の物証を自然に知っている状態を避けやすくなる。
  • LLM に「これは本人の知識」「これは噂・公的情報」と明示できる。
  • 証言で解放される場所が、話者本人の発言に紐づきやすくなる。

現在残っている設計課題

player_discovery は JSON 上に追加済みだが、探索進行そのものはまだ既存の examine_rules が担当している。つまり、探索ルールはまだ完全には一本化されていない。

次の段階では、player_discovery から調査時に得られる evidence を導出し、 examine_rules の役割を減らすか、両者の責務を明確に分ける必要がある。

ただし、n_vent_grate を調べたときに n_vent_shaft を解放するような 「エッジ発見」と「場所解放」が一致しないケースがあるため、完全自動化する場合は追加の設計が必要。

検証メモ

  • json.tool による JSON 構文チェックは通過。
  • compileall による Python 構文チェックは通過。
  • Julian の subgraph / prompt に Theatre Lobby は含まれ、Theatre Bar は含まれないことを確認。
  • Julian の発言として e26 を扱っても Bar は解放されず、Leo の発言として e26 を扱うと Bar が解放されることを確認。

LLM 実行はモデルの起動状態に依存するため、このメモでは LLM 前段のサブグラフ生成、プロンプト組み立て、場所解放ロジックを検証対象としている。

担当者向け要点

今後シナリオを編集するときは、容疑者ごとの edge list を手で更新するのではなく、 各 edge の known_by と provenance を正しく付ける。 サブグラフはロード時に自動生成されるため、JSON に保存する必要はない。
